## Context

Since the JavaFX migration, each packaging module (windows/linux/macos) builds a Spring Boot fat jar and then wraps it: launch4j on Windows, an assembly tar.gz + shell script on Linux, and macosappbundler with spring-boot-thin-layout on macOS. The release workflow (`release-build.yml`) builds all three on a single `ubuntu-latest` runner. See proposal.md — Why for the motivation and specs/platform-distribution/spec.md for the behavior contract.

## Goals / Non-Goals

**Goals:**
- One zip per platform containing a jpackage app-image: native launcher + embedded runtime.
- Release workflow publishes all three archives for a tag.
- Deterministic runtime contents (only the target platform's natives).

**Non-Goals:**
- No native installers (msi/deb/dmg), no code signing or notarization.
- No application code changes; the `time-lapse-gui` behavior is untouched.
- No jlink module modularization of the application itself (stays classpath-based).

## Decisions

1. **jpackage app-image with the fat jar as `--main-jar`.** The existing Spring Boot fat jar stays the single application artifact; jpackage wraps it with a launcher and a trimmed runtime. jdeps cannot reliably scan a Boot fat jar, so the runtime modules are pinned explicitly via `--add-modules` (java.base, java.desktop, java.sql, java.logging, java.xml, java.naming, java.management, jdk.crypto.ec, javafx.controls, javafx.fxml — adjusted if the launcher reports missing modules). *Alternative rejected:* manual jlink + custom launchers — more moving parts for no benefit at this scale.

2. **The launcher-pattern main class is a prerequisite that already exists.** JavaFX on the classpath requires a main class that does not extend `Application`; `TimeLapseMakerApplication` already does this since the migration.

3. **Platform matrix in the release workflow.** jpackage only builds images for the platform it runs on, so `release-build.yml` becomes a matrix job (windows-latest, ubuntu-latest, macos-latest); each runner executes `mvn -pl <module> -am package` for its module, zips the app-image and uploads it to the release with `gh release upload`. `gh release create` moves to a small prepare job, or the first matrix leg creates the release idempotently. *Alternative rejected:* keeping the single-ubuntu build — impossible for jpackage.

4. **Packaging modules replaced, structure kept.** Each of the three modules keeps building the fat jar (spring-boot repackage stays), then invokes jpackage through `exec-maven-plugin` bound to the `package` phase and zips the result with the existing maven-assembly-plugin. launch4j, macosappbundler, spring-boot-thin-layout, the Linux extra-resources (launcher script, .desktop) and `phase.repackage` are removed. *Alternative rejected:* folding packaging into one generic module — loses the existing per-platform dependency scoping that keeps natives deterministic.

5. **App naming.** `--name "Time Lapse Maker"`, output under `target/`, zip named `Time_Lapse_Maker-<platform>-selfcontained.zip` so the release distinguishes them from any future artifact kinds.

## Risks / Trade-offs

- [Pinned module list misses a runtime dependency] → smoke launch of each bundle in CI (matrix job launches the Linux binary headlessly with a smoke flag or at least `--version`-style run; Windows/macOS verified locally before release); missing-module errors name the module to add.
- [JavaFX from classpath inside an app-image] → already proven by the migration's fat-jar launch; app-image changes only how the classpath is assembled (launcher script generated by jpackage).
- [macOS Gatekeeper warning on unsigned zips] → accepted for now (same as today's unconfirmed .app); users right-click → Open; documented in the release notes.
- [Three runners increase CI time/cost] → each leg builds only its module (`-pl <module> -am`), so the added time is bounded.
- [Zip must preserve the macOS bundle structure] → zip on the macos runner preserves symlinks/permissions jpackage needs; verify the unzipped .app launches.

## Migration Plan

1. Same feature-branch flow; restructure the three packaging POMs, then the release workflow matrix, keeping the current release artifacts until the new ones build green.
2. After merge, the next tag publishes only the self-contained archives.
3. Rollback: revert the merge — the previous workflow still tags from `main` history.

## Open Questions

None — distribution form and replace-vs-coexist were decided with the user; remaining choices above are implementation-local.

## Implementation Notes

- The launcher cfg uses the Spring Boot `JarLauncher` as main class with the fat jar on the classpath — verified to boot the app (JavaFX natives load from the nested jars).
- `java.scripting` is required in the pinned module list (AtlantaFX stylesheet engine).
- Each bundle profile pre-deletes the app-image output directory (jpackage refuses to overwrite).
- jpackage cannot build cross-platform, hence the release matrix; the linux bundle additionally builds on every PR/dev CI because that runner is Linux.
